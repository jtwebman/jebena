# 03 — Garbage Collection

Decision doc for Jebena's memory manager. Target: Java SE 25, Zig 0.16.

## 1. What the spec enforces (the design boundary)

The JVMS is nearly silent on GC. The constraints come from the JLS and java.lang
APIs, and they are about *observable behavior*, not algorithm.

Free (implementation-defined): the collection algorithm, whether GC runs at all,
heap layout, object header format, whether objects move, pointer representation.

Enforced (must honor, and it is testable):
- No manual free. Automatic reclamation only. (JVMS 2.5.3)
- java.lang.ref reachability lattice (JLS 12.6.1): strong > soft > weak > phantom
  > unreachable, with strict ordering.
  - Soft refs MUST be cleared before OutOfMemoryError.
  - Weak cleared when only-weakly-reachable; phantom enqueued after; ReferenceQueue.
- identityHashCode stability: same value for the object's whole life, even across
  relocation by a moving collector. Constrains moving GC directly.
- Finalization / Cleaner (JLS 12.6): at most once, before reclamation, resurrection
  possible. (finalize() deprecated-for-removal but present in 25.)
- OutOfMemoryError on allocation failure; System.gc() is only a hint.
- JMM (JLS 17): concurrent barriers must preserve happens-before and final-field
  semantics. Reclamation may be aggressive (see Reference.reachabilityFence).
- Class unloading: ClassLoader + its classes + instances collectible together;
  bootstrap classes never unload.

Consequence: "way different" is allowed on algorithm, but we MUST be able to
compute reachability strength, honor reference/finalization ordering, and keep
identity hash stable. These are the conformance-critical parts.

## 2. Modern landscape (2026)

- Immix (mark-region): 32KB blocks / 256B lines, bump-pointer allocation, reuse
  partially-free blocks by skipping live lines. The modern foundation. Good
  locality + optional defragmenting copy without a strict copy requirement.
- Reference counting (RC), modernized: deferral + coalescing removes the classic
  RC overhead; combined with Immix (RC-Immix) it competes with tracing.
- Concurrent copying (ZGC/Shenandoah/C4): colored pointers + load barrier (LVB).
  Very low pause, but the read barrier is intrinsically expensive and it always
  copies. LXR argues this is the wrong tradeoff for latency-sensitive apps.
- MMTk: portable GC framework (Rust). Pluggable "plans" (MarkSweep, SemiSpace,
  Immix, GenImmix, LXR). Bindings exist for OpenJDK, V8, Ruby, Julia, JikesRVM.

## 3. LXR — the target algorithm (Zhao, Blackburn, McKinley, PLDI'22)

Premise: regular *brief stop-the-world* pauses give a more efficient path to low
latency than fully concurrent evacuation. Builds on RC-Immix.

- Heap: Immix (32KB blocks, 256B lines), lock-free global free / partially-free
  block lists, thread-local bump allocation. Dynamic overflow for medium objects;
  objects > 16KB go to a large object space.
- Identification: RC with deferral + coalescing + "implicitly dead" young-object
  optimization (young objects start RC=0 and mostly die without ever receiving a
  decrement — weak generational hypothesis). Cyclic + stuck-count garbage caught
  by an occasional concurrent SATB (Yuasa snapshot-at-the-beginning) trace using
  the *same* write barrier.
- Counts: 2-bit RC per object, stuck at 3, held in a side reference-count table
  (not the header). Min object 16 bytes; 2 bits per 16 bytes of heap.
- Write barrier: single field-logging barrier, ~1.6% overhead. Buffers old value
  (decrement) + modified field (increment); also feeds SATB and remembered sets.
  NO read barrier (unlike ZGC/Shenandoah).
- Reclamation: RC frees lines/blocks at brief STW pauses; lazy concurrent
  decrements; judicious copying — young survivors evacuated opportunistically
  (forwarding pointers), mature evacuation targets high-fragmentation blocks with
  remembered sets bootstrapped by the SATB trace.
- Pause modulation: survival-rate prediction triggers, lazy decrements,
  incremental evacuation-set copying.

Results: lusearch 1.3x heap — 7.8x throughput and 10x 99.99% tail latency vs
Shenandoah. 17 benchmarks 2x heap — beats G1 throughput by 4%, Shenandoah by 43%;
better tail latency than G1/Shenandoah/ZGC across the board. No extra hardware.

CAVEAT (critical): the paper's OpenJDK implementation DISABLED weak references,
class unloading, and compressed pointers. Those are exactly the spec-mandated
features from section 1. Porting LXR = the RC/Immix algorithm (the easy part) PLUS
the reference processing + class unloading the prototype skipped (the hard,
conformance-critical part). Budget accordingly.

## 4. Implementation strategy: native Zig vs bind MMTk

MMTk binding (VMBinding) requires the VM to implement, in Rust generics (the trait
is not dyn-compatible): VMObjectModel, VMScanning, VMCollection, VMActivePlan,
VMReferenceGlue, VMSlot, VMMemorySlice, plus alignment constants.

- Bind MMTk: get Immix/LXR/etc. "for free," research-maintained.
  Cost: a Rust dependency + an FFI boundary in the hottest paths (allocation,
  barriers). The canonical binding is written in Rust; a Zig VM would need a Rust
  shim calling back into Zig, or drive mmtk-core's C entry points while providing
  object-model/scanning callbacks. Cuts against the all-Zig, minimal-dependency,
  provenance-clean ethos. Allocation fast path must be replicated to avoid FFI.
- Native in Zig: full control, no FFI in hot path, all-Zig, matches the "way
  different memory" goal and the learning goal. Cost: implementing research-grade
  GC ourselves; the 2025 productionization paper shows this is hard even for the
  authors.

## 5. Recommendation — grow into LXR natively, MMTk as reference/fallback

Phased, native, with the interface designed Immix/MMTk-shaped from day one so we
can swap or graduate without churn.

- Phase 0 — Interface + simplest correct collector. Native semispace copying OR
  non-moving mark-sweep in Zig. Purpose: get the VM running and nail the GC
  interface (allocation, write-barrier hook points, precise root scanning at
  safepoints, reference processing, finalization/Cleaner, identity-hash handling).
- Phase 1 — Reference processing + class unloading, CONFORMANCE FIRST. Implement
  weak/soft/phantom + ReferenceQueue + Cleaner + class unloading against the spec,
  with tests, on the simple collector. This is what LXR skipped; do it early while
  the collector is simple.
- Phase 2 — Native Immix (mark-region). Modern throughput + locality foundation.
- Phase 3 — Layer RC (deferral/coalescing/implicitly-dead) + SATB trace + judicious
  copying to reach LXR natively. Re-benchmark against the differential suite.
- Fallback — if native LXR proves too costly, bind MMTk's LXR plan behind the same
  interface. Keep MMTk's design as the reference throughout.

## 6. Object model implications (decide early)

- Header must host: class pointer, thin-lock/monitor bits, GC mark / forwarding
  word, lazy identity-hash. Keep it small.
- RC counts + Immix line marks live in SIDE METADATA (like LXR's RC table:
  2 bits / 16 bytes), not the header.
- Moving GC: identity hash must survive relocation — store-on-first-request into
  header or a side table.
- Alignment: 16-byte minimum object (matches LXR's RC-table granularity).
- Plan for compressed pointers later (LXR disabled them; they interact with header
  and RC-table layout).

## 7. Test hooks (see ../TESTING.md)

- Reference processing: soft-cleared-before-OOM, weak/phantom ordering, queue
  enqueue timing, resurrection via finalizer. These are spec-mandated and where a
  clever RC collector silently goes wrong.
- OOM injection at every allocation site (SoftReference contract lives here).
- JMM/concurrency: jcstress-style litmus tests against the write barrier + STW.
- identityHashCode stability across forced GC / relocation.
- Differential vs reference JVMs; metamorphic (result invariant under -Xint vs GC
  stress).
